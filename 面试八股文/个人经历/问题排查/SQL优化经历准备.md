# SQL优化经历

## 问题
* 首先请求记录监控偶发出现慢查询
  * 通过请求记录监控能通过设备id定位到用户id
* 运维帮忙做的慢sql监控能查到带占位符的sql, 用户id能确定大部分的查询参数
  * 就是任务量很大的用户查询自己的任务

## 分析

* 第一反应是会话列表是通过用户user_id + id做的查询, 没有limit m, n的分页性能问题; 而且慢sql出现在第一页
* 首先结合索引, 先自己分析sql会如何执行, 再和执行计划进行对比
  * 个人直觉认为会通过user_id索引进行
  * 执行计划显示走全表扫描. 执行器认为扫描表的前1500多行就能找到要求的10条记录, 扫描成本低于走二级索引, extra提示走backward index scan; 个人认为是因为使用了order by id desc, 然后mysql的统计数据可能不准, 实际扫描的成本高于预期的1500多条, 导致10秒都没扫出来
* 分析为啥user_id索引成本高
  * 查询是 `select * from conversation where user_id=xxx and character_id = xxx and deleted=0 order by id desc`
  * 按理说二级索引扫描的时候就能根据二级索引隐含的主键有序规则来确定10条数据进行回表, 回表开销是很小的
  * 然后注意到二级索引并没有character_id的字段, 破案了, 因为二级索引不能判断character_id, 所以必须把用户的每一条未删除的会话都去回表, 再判断character_id是否符合条件
* 叠加mysql索引统计数据可能有问题, 导致对backforward扫描的成本估计错误, 得出了走主键倒序扫描成本更低的结论

## 为啥会有这种问题?

* 原本设计的会话列表查询是不会带character_id进行查询的, 这个查询考虑的就是不要二级索引全部扫出来每条都去回表, 所以建的索引是 user_id, deleted 两个字段
* 后来是新增了需求, 带了character_id查询, 但是没有改索引; 
* 上线之后很长时间都没问题, 用户会话不多不会走backward扫描; 因为用户和一个角色聊天就只有一个会话, 一般没人删除再重新创建; 如果要有很多会话就要很多角色, 自建角色是要花钱的
* 出问题的账号是个内部拨测账号,  定时创建角色, 会话, 会话多了之后就出现了这种问题
