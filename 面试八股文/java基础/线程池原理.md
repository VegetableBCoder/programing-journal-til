# 线程池

## 线程池的原理

* 通过Worker复用线程
  * 每个Worker对应一个线程实例, 绑定一个初始任务, 线程启动时调用runWorker
  * runWorker执行时循环取出第一个任务(如果空的就取出任务), 同时取锁, 执行取出的任务; 本质就是线程循环中队列中取出任务进行执行, 而不是执行完一个任务就退出
  * 在取出任务这个方法中决定了线程是如何阻塞, 退出的
    * 线程数<=coreSize或者并且没有开启核心线程超时, 从队列取任务会持续阻塞到有新任务到来
    * 如果超过了核心线程数, 从队列poll会带有超时时间, 超时后会返回null, 导致runWorker退出循环线程退出

## 参数说明

* 核心线程数: 当提交任务时, 如果当前线程池小于核心线程数, 就会创建新线程
* 最大线程数: 当提交任务时, 队列满了, 且线程数小于最大线程数, 会额外创建线程
* 线程存活时间: 当线程空闲, 且线程总数大于核心线程数时, 空闲时间达到阈值之后就会回收线程资源
* 任务队列: 缓存等待执行的任务
  * 有界队列: ArrayBlockingQueue, 或者带有容量限制的LinkedBlockingqueue 可以避免任务堆积太多
  * 无界队列: LinkedBlockingQueue, 容量Integer.MAX_VALUE基本无限, 所以实际上线程数无法扩容
  * 无容量队列: SynchronousBlockingQueue: 每个任务的生产者都必须确认交给某个线程处理
  * 优先级队列: 因为容量无限, 实际上也没法扩容线程数
* 线程工厂: 设置线程的名称, 优先级, 是否守护线程等
* 拒绝策略: 队列满, 线程池关闭时如何处理新的任务
  * 默认拒绝: 提交任务抛出异常
  * 丢弃: 悄悄丢弃
  * 丢弃最早的任务, 丢弃最早的任务再提交
  * 自己执行: 回压给提交任务的线程自己执行

## 参数考量

* 核心线程数: 计算型: 一般设置为CPU核数+1, 在容器环境不要用物理机算, 而是用给容器的资源来算, 如果有多个用于计算的线程池要考虑其总线程数; IO型的任务大部分都没用使用CPU资源, 在考虑计算型线程池的线程总数时可以交出1-2个核心用于IO型线程池实际占用; IO密集型线程池可以适度扩张线程池的容量, 但是也要考虑内存和事件数量的影响; 如果是主动调用服务的, 也可以结合服务的调用耗时, QPS这些考虑, 可以将调用不同服务的线程池分开隔离起来 (可以考虑占用核心数 /阻塞系数作为所有IO线程池的总线程数)
  * 内存对线程数的影响: 默认-Xss1m, 但是栈空间不是立即分配的, 而是虚拟空间; 实际占用空间会由各线程的栈深度等情况决定
* 最大线程数: 计算型一般和核心线程数保持一致, 达到能尽量跑满CPU就好, 任务堆积增加线程数也没用, 要考虑物理机性能, IO型可以合理增大最大线程数来应对突发的流量波动或网络波动
* 线程存活时间: CPU型一般核心和最大值相同, IO型要结合场景
  * 流量短周期波动的可以设置大一些
  * 周期执行的批处理, 低频任务可以设置短一些, 快速回收空闲线程(栈空间资源)
* 线程工厂: 基本是为了日志中查看线程命名; 优先级只是给操作系统提供的建议, 意义不大, 一般也不设置为守护线程; 异常处理Handler可以考虑自定义
* 拒绝策略: 
  * 提交任务时抛异常: 如转账等场景需要立即感知任务丢失的场景, 提交失败即提示失败
  * 无感知丢弃: 除了无关紧要的日志记录等一般不使用这个, 丢失了还不能感知到 
  * 丢弃最早任务: 新任务结果可以在某些场景下替代旧任务的场景, 比如定时统计; 不能在核心业务上用, 否则和无感丢弃一样出现莫名其妙的问题
  * 自己执行: 零丢失, 天然限流, 但是会阻塞其他路径的执行, 导致主路径的本职工作被阻碍, 吞吐降低
  * 自己实现: 可以选择发到kafka异步重试, 可以自己实现队列实现动态扩容队列
